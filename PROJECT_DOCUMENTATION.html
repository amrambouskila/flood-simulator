Overview — what this is & why

A self-contained, mathematically rigorous research tool that makes the hidden assumptions of radiometric dating explicit and adjustable.

The Flood-Adjusted Radiometric Dating Simulator (FAC14) is an interactive Streamlit application that demonstrates a single, focused thesis: standard radiometric dating rests on two assumptions, and if either is wrong the calculated ages are wrong — potentially by orders of magnitude. The two assumptions are (1) decay rates have always been exactly today's measured rate, and (2) the initial amount of daughter isotope was zero (or known). The simulator lets you relax both assumptions in ways consistent with the Torah's account of Creation and the Flood, then watch — using the same dating formulas geologists use — how a 5,787-year-old Earth can produce measurements that read "4.5 billion years."

It covers two independent dating regimes. Carbon-14 (thousands of years) is modelled with a pre-flood atmosphere that had less C-14 (water-vapour canopy + stronger magnetic field shielding cosmic rays), a flood event that disrupted C-14 equilibrium, and a slow post-flood recovery. Long-age isotope systems (U-Pb, K-Ar, Rb-Sr; half-lives in the billions of years) are modelled with accelerated nuclear decay during Creation Week (default 1011×) plus initial daughter isotopes from "mature creation." The key intellectual move is that the flood-adjusted model never changes the dating equations — it changes only the inputs (initial conditions, acceleration factors) fed into them.

Key concept
This is a Torah-science research tool, not a debunking gimmick. Every formula in models.py is standard nuclear-physics dating math; the flood model perturbs only the inputs. The headline demonstration: with default sliders, U-Pb reads ~4.5 billion years while the "true" age is 5,787 years — an overestimate driven entirely by the two relaxed assumptions.

Current state. Phase 1 (Streamlit interactive app) is complete and functional: a 14-parameter sidebar, six visualization tabs, headline metrics, a "The Math" tab with full LaTeX equations, Docker packaging, and cross-platform launchers. A 57-case pytest suite gives 100% statement + branch coverage on the core physics module. Phase 2 (FastAPI + React) and Phase 3 (extended geological modelling) are planned but not started.

Watch out — two code paths, one is broken
The Streamlit path (app.py → models.py) is the live, tested, shipping product. A second CLI path (fac14_main.py → simulation.py → visualization.py) is legacy and currently fails at import because it imports a create_model symbol that no longer exists in models.py. Treat the CLI as not-yet-working. See Core modules and How to edit for details.

Architecture

One Streamlit script reads sliders, builds two model objects from models.py, and renders six Plotly tabs. Everything is recomputed from scratch on every interaction — no state, no database, no network.

The shipping architecture is a classic Streamlit "single rerun" model. When any sidebar slider changes, Streamlit re-executes app.py top-to-bottom. The script instantiates a FloodAdjustedModel (C-14) and a LongAgeRadiometricSuite (which itself wraps three RadiometricSystem objects), calls their compute methods to produce NumPy arrays and summary dicts, and feeds those into Plotly figures and Streamlit metrics/tables. The compute layer (models.py) has zero dependency on Streamlit, which is exactly what makes Phase 2 (wrapping the same physics in FastAPI) a clean refactor rather than a rewrite.

Core modules & classes

All real logic lives in models.py. The Streamlit script is glue; the CLI trio is legacy. Each drill-down below cites exact lines.

Constants & isotope table models.py:1–42

The module opens with three groups of module-level constants that are the single source of truth for every number in the simulation.

  • C-14 constants (models.py:3–6): CARBON_14_HALF_LIFE = 5730, LAMBDA = ln(2)/5730, STANDARD_ATMOSPHERE_C14_RATIO = 1.0.
  • Torah timeline (models.py:8–14): FLOOD_YEAR = 1656, CURRENT_YEAR = 5787, YEARS_SINCE_FLOOD = 4131 (derived), CREATION_WEEK_YEARS = 6/365.25, FLOOD_YEAR_YEARS = 1.0, FLOOD_DURATION_DAYS = 365.
  • ISOTOPE_SYSTEMS dict (models.py:17–42): the three long-age systems with parent, daughter, half-life, derived lambda, and human-readable descriptions.
StandardModel models.py:45–60

The baseline "uniformitarian" C-14 model. It assumes a constant atmospheric C-14 ratio of 1.0 and a constant decay rate. Two pure methods:

  • calculate_age(c14_ratio) → -ln(ratio) / LAMBDA; returns inf for non-positive ratios (models.py:52–56).
  • predict_ratio(age) → exp(-LAMBDA * age) (models.py:58–60).

It is the reference curve in the "C-14: Ratio Over Time" tab and the formula the flood model's standard_date_for_true_age applies to its own (flood-perturbed) measured ratio.

FloodAdjustedModel — the C-14 engine models.py:63–219

The C-14 model with nine adjustable parameters (set as instance attributes by app.py). It computes, for any true age, what C-14 ratio you would actually measure today and therefore what age standard dating would mistakenly report. The pipeline:

  1. effective_initial_c14(true_age) (models.py:146–165) — branches on whether the organism is pre-flood, mid-flood, or post-flood and returns its C-14 ratio at death.
  2. predict_measured_ratio(true_age) (models.py:167–189) — applies standard decay exp(-LAMBDA·true_age) to that initial ratio, then a temperature/pressure correction for samples near the flood window, floored at 1e-15.
  3. standard_date_for_true_age(true_age) (models.py:191–202) — feeds the measured ratio into the standard formula -ln(ratio)/LAMBDA. The gap between this and true_age is the dating error.
  4. generate_comparison_data(max_true_age, steps) (models.py:204–219) — vectorizes the above across a linspace of true ages into the arrays the charts consume.

Three private helpers carry the physics:

_cosmic_ray_shielding · models.py:90–97(1/magnetic_field_factor) · (1 − water_vapor_canopy) — pre-flood shielding that lowered initial C-14.
_temperature_pressure_factor · models.py:99–120Temp + hydrostatic-pressure + burial factors that further age flood-window samples.
_post_flood_c14_buildup · models.py:122–144Exponential approach to modern equilibrium with tau = equilibrium_years/3, scaled by volcanic dilution + ocean reservoir, clamped to 1.0.
Watch out — physical realism vs. demonstration
The temperature/pressure/burial factors and the volcanic/ocean multipliers are modelling choices, not derived from first principles. They are deliberately tunable knobs to show direction and magnitude of effects. The radioactive-decay math (exp(-LAMBDA·t)) and the dating formulas are the rigorous, non-negotiable parts; the environmental modifiers are illustrative.
RadiometricSystem — the long-age epoch engine models.py:236–378

Models one parent→daughter system (e.g. U-238→Pb-206) walking normalized parent P and daughter D through four biblical epochs, then reports what standard radiometric dating would compute. Constructed with a system_key, an initial_daughter_ratio (mature-creation daughter present at t=0), and two log10 acceleration factors.

The core is _evolve() (models.py:271–302), which applies the same per-epoch update four times. For each epoch with duration dt and acceleration A:

Because every unit of parent that decays is added to daughter, P + D is invariant — this is the mass-conservation property the test suite checks at every epoch boundary. The four epochs (models.py:277–300):

EpochDuration (dt)Acceleration (A)
Creation Week6/365.25 yr10^creation_acceleration_log10 (default 1011)
Pre-FloodFLOOD_YEAR − CREATION_WEEK_YEARS ≈ 1656 yr1×
Flood Year1.0 yr10^flood_acceleration_log10 (default 1×)

Reporting methods: apparent_age() (models.py:304–309) = (1/lambda)·ln(1 + D/P); daughter_parent_ratio() (:311–315); and get_epoch_breakdown() (:317–378), which re-runs the walk and emits a per-epoch dict (name, duration, acceleration label, P_after, D_after, consumed) for the tables.

Why Creation Week does all the work
For Gyr half-lives, the pre-flood and post-flood epochs (thousands of years) decay a negligible fraction of parent. The 6-day Creation Week epoch — at A = 1011 — has an effective A·lambda·dt large enough to convert a meaningful fraction of parent into daughter, equivalent to billions of years at normal rates. That, plus the initial daughter ratio, produces the ~4.5 Gyr apparent age.
LongAgeRadiometricSuite models.py:381–421

A thin aggregator that builds one RadiometricSystem per entry in ISOTOPE_SYSTEMS with shared acceleration settings and per-system initial daughters. Class-level defaults (models.py:384–390): creation accel 11.0, flood accel 0.0, and initial D/P of 0.55 / 0.30 / 0.10 for U-Pb / K-Ar / Rb-Sr. Provides apparent_ages() (dict) and summary_table() (formatted rows for the Big Picture tab).

format_age helper models.py:224–233

Pure display helper: turns a number of years into "X.XX billion years", "X.X million years", "X.X thousand years", or "N years". Used throughout app.py and in summary_table().

app.py — the Streamlit front end app.py:1–604

The math — formulas & key logic

Every formula below is standard radiometric dating math. The flood model changes only the inputs. These are the source of truth for any reimplementation (e.g. Phase 2 in TypeScript).

Carbon-14 dating

Standard age (what the model assumes): t = −ln(R_measured) / λ, with λ = ln(2) / 5730 and R_measured normalized so today's atmosphere = 1.0.

Full equation (honest version): t = −ln(R_measured / R₀) / λ. If the true initial ratio R₀ < 1.0, standard dating overestimates age by exactly −ln(R₀) / λ years — independent of the sample's real age. This single term is the entire C-14 error mechanism.

Initial ratio at death depends on the epoch (models.py:146):

  • Pre-flood: R₀ = pre_flood_c14_ratio × (1/magnetic_field_factor) × (1 − water_vapor_canopy)
  • During flood: R₀ = pre_flood_c14_ratio × 0.5 (severe disruption)
  • Post-flood: exponential buildup with tau = post_flood_equilibrium_years / 3, scaled by volcanic dilution and ocean reservoir.

Long-age radiometric dating

Standard apparent age for any parent→daughter system: t = (1/λ) · ln(1 + D/P), with λ = ln(2)/half_life. It assumes all daughter came from in-situ decay (no initial D) and constant λ.

How to run it

Docker via the launcher is the primary path; a plain streamlit run works for local dev.

Docker (recommended)

  1. Ensure Docker Desktop is running.
  2. Run fac14_service.sh (macOS/Linux) or fac14_service.bat (Windows).
  3. The launcher runs docker compose up --build -d, prints the URL, and auto-opens http://localhost:5250.
  4. At the prompt, choose a control: k stop (keep image), q stop + remove image, v stop + remove image + volumes, r full reset & restart.
Launcher menu differs from the house standard
These launchers implement k/q/v/r where r is a full reset (down + remove images + rebuild + relaunch) and loops. The owner's canonical template defines r as a lightweight restart (down + up). Functionally fine, but the semantics of r here are heavier than the template's. The bat file's q and v both jump to image-removal cleanup.

Local (no Docker)

  1. pip install -r requirements.txt
  2. streamlit run app.py → opens on Streamlit's default http://localhost:8501.
Do not expect the CLI to run
python fac14_main.py --age 5000 --model flood --plot (as printed in the README/CLAUDE) fails at import today. Use the Streamlit app for all real work until the CLI is repaired (see How to edit).

How to edit & extend it

Concrete recipes for the common changes, with the exact files to touch and the conventions to respect.

Add a new long-age isotope system (e.g. Sm-Nd)
  1. Add an entry to ISOTOPE_SYSTEMS in models.py:17 with parent, daughter, half_life, lambda = np.log(2)/half_life, description, science_says.
  2. Add a default initial D/P to LongAgeRadiometricSuite.DEFAULT_INITIAL_DAUGHTERS (models.py:386).
  3. Add a sidebar slider in app.py:63–82 and pass it into the initial_daughters dict at app.py:174.
  4. The Big Picture bar, Long-Age tab selectbox, and Math tab loop over ISOTOPE_SYSTEMS automatically — but the Big Picture bar's explicit name/value/color lists (app.py:255–257) and the headline metric row (app.py:217) are hand-built for three systems; extend those too.
  5. Add a parametrized test case automatically (most tests already iterate list(ISOTOPE_SYSTEMS.keys())) and run pytest --cov to confirm 100% holds.
Watch out
Phase constraints (CLAUDE.md §2) explicitly defer "additional isotope systems beyond U-Pb, K-Ar, Rb-Sr" to Phase 2. Adding one is a scope decision, not just a code change.
Change a parameter's slider range or default

Edit the relevant st.sidebar.slider(...) in app.py:43–153. The canonical range table lives in the master plan (FLOOD_SIMULATOR_MASTER_PLAN.md §5) — keep them in sync; the post-tool-use hook (post-tool-use.cjs) reminds you to verify slider ranges match the master plan when app.py is edited. If you change a model default (not just the slider), edit the attribute in FloodAdjustedModel.__init__ (models.py:76–88) and update the matching assertion in test_models.py:74.

Adjust the physics / add an epoch

The decay math lives entirely in models.py. To add or change an epoch, edit both _evolve() (models.py:271) and get_epoch_breakdown() (models.py:317) — they duplicate the walk (one returns final P/D, the other returns per-epoch rows). Preserve the mass-conservation invariant (P + D constant) or test_models.py:192 will fail.

Key concept
Keep every numerical literal named and documented (no magic numbers in computation), keep domain variable names (P, D, lam, R, A, dt), and ensure any new formula traces to standard dating math. The data-driven-check and validation-protocol skills enforce this.
Fix the broken CLI path

  2. Rewrite the CLI on the new API (preferred): rewrite simulation.py to drive FloodAdjustedModel directly (set attributes, call standard_date_for_true_age / generate_comparison_data), then add a tests/test_simulation.py and pull simulation into the coverage source in pyproject.toml:13.

What's covered

Six test classes mirror the public surfaces: TestConstants, TestStandardModel, TestFloodAdjustedModel, TestFormatAge, TestRadiometricSystem, TestLongAgeRadiometricSuite. Highlights:

  • Reference values: one half-life recovers 5730 yr (:45); predict_ratio(5730) == 0.5 (:56); calculate/predict are inverses across ages (:64).
  • Mass conservation: P_after + D_after constant across all four epochs, parametrized over all systems (:192).
  • Analytic recovery: zero accel + zero initial daughter recovers the elapsed epoch time (:182).

Domain glossary

Terms a newcomer needs to read the code and the UI.

Radiometric dating
Estimating a sample's age from the ratio of a radioactive parent isotope to its decay daughter, assuming a known decay rate and initial conditions.
Half-life (t½)
Time for half of a parent isotope to decay. λ = ln(2)/t½.
Decay constant (λ, LAMBDA)
Probability per unit time that a nucleus decays; the slope of exponential decay.
Parent / Daughter (P / D)
The decaying isotope (P) and the product it becomes (D). Apparent age comes from the D/P ratio.
Initial daughter ratio
Daughter isotope already present at t=0 ("mature creation"). Standard dating assumes this is zero.
Acceleration factor (A)
Multiplier on the decay rate during an epoch. Default 1011× during Creation Week.
C-14 (radiocarbon)
Carbon-14, t½ = 5730 yr. Dates organic material up to ~50,000 yr.
R₀ / R_measured
Initial vs currently-measured C-14/C-12 ratio, normalized so today's atmosphere = 1.0.
Water vapour canopy
Hypothesized pre-flood atmospheric water layer that shielded cosmic rays, lowering C-14 production.
Epoch
One of four modelled time spans: Creation Week, Pre-Flood, Flood Year, Post-Flood.
The Flood (Mabul)
Year 1656 from Creation; the catastrophic event that disrupted C-14 equilibrium.
Isochron / Concordia
Multi-sample dating plots (Phase 3). An isochron's slope gives an age; a concordia compares two U decay chains.
Apparent age
What standard dating reports — distinct from the model's "true age" of 5,787 years.
